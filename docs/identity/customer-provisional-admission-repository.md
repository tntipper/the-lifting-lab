# Disabled durable provisional admission intents

`lib/identity/customer-provisional-admission-repository.ts` and migration `202609170008_customer_provisional_admission_repository.sql` implement the durable intent **before** one Supabase authorization GET. They create no routes, provider, LOGIN, credential, application session or network request. The adapter is synthetic-only and default disabled; SQL has its own disabled control. `liveEnabled:true` cannot activate it. This is an admission-only slice, separate from 005 connections, 007 subjects and the later inner Shopify/final exchange stores.

## Concrete API and authority

The constructor captures a dedicated bounded pool, an injected envelope vault and one exact protected staging application origin. It computes a configuration hash from the version, that origin and fixed staging project/provider/broker parameters. SQL independently checks the origin family and configuration hash, then binds every operation to the exact retained configuration. The existing session-reader and encryption APIs are unchanged.

`createProvisionalAdmissionMetadata` is a pure helper used **before** attempting persistence. It projects and hashes the immutable transaction ID, browser-secret hash, exact origin/configuration, explicit mode, original migration UUID/session/access-token hash (or null for sign-in), application PKCE challenge and five-minute maximum lifetime. No UUID, verifier, secret, proof or time is generated by this helper. Its output gives the caller the original quarantine binding even if `prepare` never commits.

| Method | Durable behavior |
| --- | --- |
| `prepare({ operationId, metadata, applicationPkceVerifier })` | Verify verifier/challenge consistency, seal the verifier, reserve never-reused transaction and PKCE challenge, commit `prepared`. |
| `claimAdmission({ ...binding, operationId, currentMigrationProof })` | One `prepared → admission_inflight` transition; return acknowledged metadata/fence/generation, never a verifier. |
| `finishAdmission({ ...binding, sameOperationId, fence, generation, admission })` | Revalidate the normalized admission URL/query, persist the exact outer tuple/hash, commit `admitted`. |
| `readIntent(binding)` | Read immutable metadata, persisted state, current fence/generation, database observation time and any admitted outer tuple. No verifier or ciphertext is returned. |
| `holdOperation({ ...binding, operationId, fence?, generation? })` | Quarantine the original intent or persist an unknown-prepare tombstone; reject transplanted or stale authority. |
| `cancel({ ...binding, newOperationId })` | Fence the original intent, advance its generation and invalidate retained PKCE material. |

`binding` contains `transactionId`, `browserHash`, `configHash`, `intentHash` and `applicationPkceChallenge`. `claimAdmission` and its `finishAdmission` intentionally share one operation ID. Other recorded phase/flow reuse fails. Cancellation and known holds remain possible at normal capacity and when SQL is disabled. No expiry or failed acknowledgement makes an inflight claim available again.

For migration, `currentMigrationProof` is the actual trusted session verifier's narrow metadata plus the server-computed access-token hash. SQL checks the exact original UUID/session/hash, authenticated audience/issuer/non-anonymous status, authentication recency, credential expiry and a check age under five seconds. **The database does not verify a live session or token.** The future coordinator must obtain the actual reader result and re-read the original request-scoped token before dispatch; equality with a stored UUID/hash is not a substitute. Sign-in requires null original owner and null migration proof. No invented owner or Auth foreign key is introduced.

## Encryption and recovery

Only `{ verifier }` is encrypted here, using the existing authenticated envelope primitive with a distinct `tll-provisional-admission/v1` purpose. AAD binds the staging project, application-PKCE purpose, transaction, configuration, browser hash, intent hash and initial generation zero. SQL receives only a bounded authenticated-envelope representation; it never receives the raw verifier. Raw access tokens, browser secrets, code strings, inner Shopify verifier/nonce/tokens, final sessions, emails and provider errors are absent. The SQL executor cannot read ciphertext tables and the API has no verifier-decryption method. A future final-exchange claim and decryption policy require separate review.

Known hold/cancel transitions clear the ciphertext while retaining immutable metadata, operation history and any observed outer response. An unknown-prepare tombstone retains only the original binding and reserved PKCE challenge. Retention is intentionally conservative: no cleanup automatically frees transaction IDs, operation IDs, PKCE challenges or outer states.

One short control-row lock serializes transitions, caps and uncertainty. The database samples `clock_timestamp()` after locking. The adapter owns BEGIN/COMMIT, uses server lock/statement/idle timeouts, returns only after acknowledgement, destroys uncertain connections and exposes fixed errors with no retry. The injected pool must additionally bound connection/acquisition/query/lease time. On failure the caller must persist `holdOperation` using the original binding and any observed fence/generation. If holding fails, keep all output held and require durable recovery; never repeat the upstream GET or regenerate/reuse the verifier.

`readIntent` remains available after SQL disable, expiry, hold or cancellation so recovery can inspect the immutable record. An `admitted` read after a lost finish acknowledgement **does not authorize HTTP, broker registration, a browser redirect or authentication**. The later two-store bridge must verify the exact acknowledged 007 registration and its current state. A metadata read cannot prove that this bridge exists. This repository neither calls nor mutates 007. Propagating a cancellation/hold to an already registered outer broker flow remains a coordinator requirement.

`finishAdmission` accepts exactly the normalized output of the reviewed Supabase admission transport: exact application origin/path, client, callback, scope, UUID state, S256 method and a challenge distinct from application PKCE. URL/query disagreement, extra or duplicate parameters, noncanonical encodings and credential-bearing fields are rejected. SQL independently validates the structured tuple and its hash, including globally unique retained outer state/hash, before acknowledgement. The raw upstream response is never stored.

## Private schema, operator and bounds

The independent `tll_provisional_private` schema has a NOLOGIN owner and a separate NOLOGIN executor. The executor receives only schema USAGE and EXECUTE on the transition function. Browser/service roles and the 005/007 executors have no effective schema/table/sequence/helper access. Scoped creation ACLs, including indirect inherited default grants, are removed. Private tables have RLS; only the SECURITY DEFINER owner performs transitions.

The migration installer retains aggregate status/control and ADMIN-only executor delegation, with no inherited executor or SET authority. Operator functions require the exact session role OID; SET ROLE does not impersonate it. The migration creates no runtime LOGIN. A separately reviewed pool, keyring and hosted role binding remain necessary.

Normal admission is capped at 500 preparations per UTC day, ten per browser hash per ten minutes, 10,000 retained intents and 100,000 operations. Unknown quarantine can use up to 20,000 retained intents, while operation capacity remains. Known intents can each add at most one terminal revocation operation beyond the normal cap; this reserves bounded headroom of at most 20,000 additional ledger rows. Thus holding/cancelling remains durable at normal capacity, and its operation ID still cannot be reused on another flow. There is no unbounded retry or tombstone growth. Operator disable waits for admitted SQL before preventing subsequent material transitions.

## Local verification and remaining gates

The guarded setup uses only the existing local `tll-stage0-postgres` PostgreSQL17 container and creates `tll_provisional_repository` once, marked `tll-provisional-admission-repository-synthetic-v1`. It refuses existing databases, remote Docker endpoints and unexpected images. It creates only provisional-specific NOLOGIN roles, and reuses existing browser fixture roles. Tests clear only this marked fixture's synthetic rows and leave it disabled; they do not alter 005/007 or hosted staging.

```sh
node tests/provisional-admission-repository/setup.mjs --create-once
node tests/provisional-admission-repository/migration-regression.mjs
node --experimental-strip-types --test tests/provisional-admission-repository/acceptance.test.mjs
node --experimental-strip-types --test tests/customer-provisional-admission-repository.test.mjs
npm run typecheck
```

**Validation:** 22 actual PG17 cases, eight offline adapter cases, the canonical non-superuser migration regression, typecheck and focused lint pass.

The actual PG tests exercise the concrete adapter through independent persistent connections, including encryption/AAD, immutable bindings, migration token-hash/recency guards, URL/tuple validation, concurrent claims, delayed commits, lost pre/query/commit acknowledgements, metadata-only reads, expiry, quota and privilege boundaries. The migration regression reconstructs the canonical migration inside a rollback, checks hostile inherited ACLs and tests narrow grant/revoke with an uncommitted NOLOGIN probe. Offline tests verify commit ordering, projection, configuration capture, response validation and redaction.

These tests do not establish hosted pooler interoperability, actual session verification, actual upstream side effects or a physical database crash. The provider/route setup, request-scoped coordinator, exact 007 registration bridge, inner Shopify state/token store, final application exchange/verifier release, authoritative identity promotion, browser persistence, owner-wide cancellation/logout, retention/recovery procedure and actual hosted journey remain open. No current snapshot or successful local test authorizes activation.

# Disabled subject-only OAuth2 broker protocol

`lib/identity/customer-subject-broker.ts` implements the outer **Supabase Auth → TLL broker** protocol with injected trusted ports. It has no routes, database adapter, identity creation/linking, key provisioning, provider configuration or network calls. Only `syntheticExecution:true` permits the test ports to execute; `liveEnabled:true` cannot activate it. The Map repository under `tests/fixtures/` is a non-durable model and must never be deployed.

The intended, **unregistered** broker client ID is `tll-staging-subject-broker-v1`; it is independent of Shopify's Confidential client. Its sole callback is `https://qdmvngjwkcsilzmqksme.supabase.co/auth/v1/callback`, scope `subject`, response type `code`, and challenge method `S256`. This pins the protocol while remaining separate from any approval to configure a client. A later provider must use custom OAuth2, `email_optional:true`, PKCE enabled, and no mapping/allowlist that reintroduces email or Shopify tokens.

## Trusted server inputs and browser admission

`serverRegistration()` is supplied only by the server that initiated the Supabase authorize or manual-link request. It reads the retained immutable registration receipt, including the exact returned authorization query, application PKCE challenge, browser transaction and mode; a browser-supplied URL is not an equivalent receipt. It remains readable for readiness/cancellation and is not itself a one-use consumer. For migration it also records the exact original UUID/session that authorized manual linking, which `currentSession()` must independently prove again. The protocol exposes no method accepting a caller's approval flag, target email or proposed user UUID.

`currentBrowser()` must read an HttpOnly, Secure, SameSite browser transaction secret from the same-origin request after the route's CSRF/origin checks. Secrets are 256-bit random values; only their hashes go to the broker repository. Transaction IDs alone do not grant admission. The core compares the current browser and exact registered outer request before `registered → admitted`. The application PKCE challenge, GoTrue's outer challenge and Shopify's inner challenge must differ; the token endpoint verifies the outer challenge against the supplied verifier.

The reviewed upstream revision `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3` generates a separate provider PKCE verifier, uses a UUID flow state and forwards the corresponding S256 challenge. During callback, it supplies `code_verifier` to the code exchange. This is distinct from the application's final Supabase session PKCE exchange. [Authorization construction](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/external.go#L93), [exchange](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/external_oauth.go#L88).

## State transitions and outputs

| Transition | Required authority and result |
| --- | --- |
| registration → admitted | Exact server registration, browser hash, fixed client/callback/state/S256 and unexpired attempt; one admission. |
| admitted → verifying | Durable one-use claim with a broker-specific fence and current generation; no reclaim of uncertain work. |
| verifying → ready | Trusted Shopify proof receipt bound to this exact inner transaction, issuer/shop, independent PKCE and recent verification; migration additionally requires the same original recent Supabase UUID/session. Reserve/reuse the stable opaque subject and persist the code hash before returning the callback URL. |
| ready → token issued | Confidential Basic authentication plus matching code, callback and S256 verifier; commit code consumption and the new bearer hash before returning OAuth JSON. |
| token issued → consumed | Exact bearer, unchanged generation, current readiness and bearer deadlines; commit consumption before returning `{"sub":"tllb_<opaque identifier>"}`. |
| any outstanding state → cancelled/held | Cancellation, owner logout, expiry, invalid proof, conflict or uncertain write prevents further use. Neither code nor bearer is restored. |

Only the token response deliberately contains a **broker-only** bearer for the authenticated machine caller. It contains no refresh token, ID token, Shopify token, email or account-management scope. The bearer has a 60-second maximum lifetime but loses authority earlier when its readiness expires or the transaction is consumed/cancelled. Code reuse denies another exchange and invalidates any outstanding bearer. The userinfo result has exactly one field, `sub`; errors contain fixed OAuth codes, never raw provider/database messages or request values. All protocol responses specify `no-store` and `no-cache`.

Basic credentials follow OAuth's form-encoding rules. The core accepts exactly one authorization header; duplicates, malformed encoding, mixed body credentials and wrong client/secret fail before code consumption. Go's OAuth client tries Basic first and may retry with body credentials after an error; this core deliberately does not support the fallback or repeat an uncertain exchange. A new browser transaction is required. [OAuth client authentication and token exchange](https://www.rfc-editor.org/rfc/rfc6749#section-2.3.1), [pinned Go client behavior](https://github.com/golang/oauth2/blob/v0.36.0/internal/token.go#L199), [S256 verification](https://www.rfc-editor.org/rfc/rfc7636#section-4.6).

Supabase's custom provider calls userinfo before handing its upstream `provider_token` to the application. The broker bearer must therefore already be spent when browser session persistence occurs. A later SSR adapter must also strip this spent token as defence in depth. This module does not change Supabase cookie/session handling. [Custom provider userinfo](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/provider/custom_oauth.go#L73), [provider-token handoff](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/token.go#L270).

## Identity and readiness limits

The stable broker subject is a random reserved identifier keyed privately to `(shop, issuer, Shopify subject)`. It must not be regenerated on every login or derived from email. `verifiedShopifySubject()` is a private proof adapter, not a public JSON input: it must already have performed real ID-token cryptographic/nonce checks and committed the related inner transaction. The core projects only its narrow receipt fields; token-bearing extras never enter repository requests.

New sign-in reserves a **provisional subject with no invented Supabase UUID**. Migration records a pending reservation for the original verified UUID; it does not mark a link complete. Conflicting target reservations and unresolved provisional-to-migration ownership remain held. No `auth.users`/`auth.identities` writes or calls into the existing UUID connection ledger occur. Final authoritative Supabase identity reconciliation, owner binding and commerce-vault release remain separate work.

Readiness lasts no more than five seconds after the Shopify proof check and, for migration, no more than five seconds after the original session check. It is also capped by the attempt expiry, authentication recency and both credential expiries. Token issuance and userinfo must recheck that **same** deadline against database time; they may not restamp the proof or widen the deadline to the bearer TTL. A cold start may legitimately hold the flow. This proves a bounded recent observation, not an upstream revocation query at userinfo. Coordinated logout must cancel all pending owner records through a reviewed gateway; browser cancellation handles its particular transaction.

## Durable adapter and mounting gates

The repository interface specifies acknowledged commits, database time, immutable requests, uniqueness, private grants, operation IDs, independent fences/generations, one-use consumption and uncertain-outcome quarantine. The future SQL adapter must enforce these itself across processes; TypeScript and the test Map do not supply durability. Do not reuse a connection-ledger fence as broker authorization or infer an outer subject reservation from a connection table. Persistent quotas, retention, privilege tests, concurrency and crash tests are required with the adapter.

An operation-ID tombstone alone is insufficient when a failed write never recorded its ID. Quarantine additionally binds the immutable transaction/browser/outer-request receipt, or the exact code/registered-client/callback/S256 or bearer binding. It must stop **new operation IDs on that same flow** under the same transition lock, including late commits. Known fences/generations must match the observed flow; missing values do not authorize guessing a current generation. Only the original admission proof and a never-reused transaction ID permit quarantining before a claim acknowledgement. New recovery requires a new browser transaction, not clearing the quarantine. If quarantine persistence itself fails, output stays held and credentials/subject are not released; an operator must establish durable state before attempting recovery.

For protected Vercel previews, the proposed split keeps browser authorization/Shopify callback in Next and serves only token/userinfo from narrowly authenticated staging Edge handlers. It does not weaken Vercel protection or embed a bypass key. No endpoint is mounted here. HTTP adapters still need strict methods/content types/body limits, transport security, origin/CSRF enforcement, no credential-bearing logs and an appropriate private gateway. Browser-facing routes must never serialize trusted registration/proof ports or the machine token result.

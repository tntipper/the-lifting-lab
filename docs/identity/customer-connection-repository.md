# Disabled durable customer connection repository

Migration `202609150005_customer_connection_repository.sql` and `createCustomerConnectionRepository` implement the existing server domain's private PostgreSQL repository. They add no HTTP route, login, provider request, scheduled worker, browser capability or account connection. Both the adapter and database control default disabled. `liveEnabled:true` cannot activate the adapter. Explicit synthetic execution is a test port, not a sandbox against a deliberately supplied remote pool. No hosted migration or real customer account has been exercised by this work.

## Storage and authority

The private `tll_customer_private` schema contains a disabled control row, one owner/generation row per `(Supabase user, staging shop)`, attempts, immutable subject reservations/connections, and a monotonic fence sequence. The migration pins the current synthetic Shopify shop and issuer. Owner UUIDs reference `auth.users`; no email mapping, `auth.identities` write or Auth session mutation occurs. Deleting an Auth user administratively cascades this user's repository data, including the subject reservation. That destructive lifecycle needs an explicit retention/unlink policy before real use.

`tll_customer_owner` is NOLOGIN with ownership only of the new private objects. `tll_customer_executor` is NOLOGIN and receives only schema usage and execution of `repository(text,jsonb)`. It has no direct table, column, sequence or control-write authority. Browser and ordinary service roles have no effective schema/function/data rights. Creation/default ACLs are removed from the scoped objects; postflight checks effective grants including inherited access, column grants and PostgreSQL17 MAINTAIN. RLS is enabled with no client policies. The owner deliberately bypasses its own table RLS inside the definer function. All object names/search paths are fixed; caller input is data.

The migration supports PostgreSQL17+ and non-superuser CREATEROLE/schema owners. It creates the private owner and executor directly, retains one bootstrap-granted ADMIN-only membership on each, and removes only its temporary self-granted owner membership before commit. Neither role is inherited or usable through SET ROLE by default, and no runtime LOGIN is provisioned. The installing operator can deliberately delegate executor access or acquire temporary SET-only owner authority for a future reviewed migration. This is trusted provisioning power, not a security boundary against that operator. Its ordinary SQL access remains only schema USAGE and EXECUTE on the two operator functions; it cannot read private tables, inspect encrypted material, call the repository executor or CREATE objects without a deliberate further grant change. See [repository migration authority](repository-migration-authority.md) for exact grantor/retirement semantics and upgrade proof. Existing platform helpers, other migrations and shared default privileges are untouched. Installation fails on preexisting scoped objects or missing prerequisites; it is a one-time migration-history operation. No already applied migration is replayed by this policy change.

The installing operator can call `SELECT tll_customer_private.operator_status()` for enabled state, database change timestamp, a bounded nonsecret reason code, and aggregate owner/attempt/connection status counts. It returns no identifiers, subjects, envelopes or key metadata. `SELECT tll_customer_private.operator_set_enabled(false, 'release_hold')` disables use; an explicit `true` enables the database gate only after the separate runtime/key/acceptance approvals. Both functions require the exact recorded **session user** OID as well as their narrow EXECUTE grant. `SET ROLE` from a different session is insufficient. Verify that the real migration operator is also the later SQL session user before installation; an operator change requires a reviewed migration using explicit temporary owner authority and complete retirement checks. The ordinary executor and all browser/service roles cannot call either function. Missing control data fails closed, rather than allowing the operator to recreate it through the control function.

Enable/disable is serialized against admitted SQL using the control row lock. A successfully acknowledged disable waits for earlier admitted repository transactions to finish and blocks later claims/material writes. It cannot cancel an external provider request already sent following an earlier committed claim. Logout and same-fence uncertainty holds remain available while disabled. The control row stores only the latest timestamp/reason, not a complete audit history; retain deployment/operator evidence separately without secrets. These aggregate controls provide safe observation and suspension, not a general identity-reconciliation or token-recovery API.

The executor is trusted server infrastructure. Its UUID/session arguments must come from the separately verified `currentSession` adapter. They are not a public authentication mechanism. The repository binds pending callbacks to the exact owner/session and configuration; refresh and connection logout are user/shop scoped after a valid session proof. A compromised database administrator or authorized server is outside this least-privilege boundary.

## Transactions, expiry and uncertainty

Every operation takes the same owner/shop row lock before reading the current generation and changing attempts/connections. Database `clock_timestamp()` is sampled **after lock acquisition**. Caller `now` arguments are ignored; they exist only for compatibility with the domain port. A start timestamp must be within five seconds of database time, and attempt expiry cannot exceed five minutes. Refresh leases are at most 60 seconds. Domain/session/configuration expiry checks still apply separately.

- Concurrent starts reserve one pending/exchanging operation. State hashes and attempt UUIDs cannot be replaced. Only one exact owner/session/config claimant changes pending to exchanging.
- Exchanging is consumed once. Expiry or a hold permits a fresh authorization attempt; it never permits the same code/state to exchange again.
- Completion reserves both `(shop, issuer, subject)` and `(shop, user)` under unique constraints. Exact reauthentication can replace held/logged-out/active material for that binding. It cannot change its subject or take another user's reservation, and it cannot replace a connection while refresh is outstanding.
- Refresh commits a new monotonic fence and lease before returning encrypted material to the adapter. Expired refreshing becomes held with its full token bundle removed; the old refresh token is never retried automatically. A new, verified authorization is required.
- Finish checks the current fence, live expiry and unchanged generation. A late finish cannot undo logout. Same-fence holds also quarantine a successful commit whose acknowledgement was lost. An older hold cannot disable a newer operation.
- Logout tombstones use, advances the owner generation, cancels attempts and fences refresh. Repeating logout is idempotent. It preserves the identity reservation and returns upstream logout `pending`; no upstream completion is claimed.

The adapter exclusively leases an idle client from an injected `CustomerRepositoryPool`, starts an explicit transaction and awaits COMMIT before decrypting/exposing claim material. Failed/uncertain clients are discarded. A lost claim/finish acknowledgement triggers a separate same-fence hold after releasing the first connection. If that hold also fails, exchanging/refreshing stays unreclaimable; disable use and inspect the exact operation before reauthentication. The adapter never retries an uncertain exchange or token refresh. Process death immediately after a successful COMMIT can still prevent the hold; lease/attempt expiry prevents reuse of that claim, and a fully committed active bundle can be superseded only under a newer fenced operation. Postgres host failover/durability and driver-specific pooling behaviour need separate acceptance.

## Encryption and required injections

PKCE verifier/nonce and the complete attempt snapshot are encrypted before SQL. Access/refresh/ID tokens, original nonce, scope provenance and refresh-token provenance are likewise encrypted before SQL. Plaintext token bytes never appear in SQL arguments or columns. The separate logout envelope contains only the ID token, with its own purpose and retained claim context; logout removes the general token bundle. No logout-intent read/worker API is included.

The shared [AES-GCM vault](envelope-vault.md) authenticates environment, purpose, owner/subject binding, configuration and exact claim identity/fence. A ciphertext moved between owners, operations, configurations or purposes fails. The adapter snapshots input before asynchronous calls and preserves the two provenance objects inside the encrypted bundle. Database identity/configuration/expiry metadata remains readable to the privileged owner; it is not placed in public tables or customer DTOs.

Before any staging mount, supply a reviewed dedicated database LOGIN with membership only in the executor, a compatible idle-client pool with bounded connection acquisition and verified TLS/project binding, and a server-held keyring using separately protected versions. The interface is compatible with `pg.Pool`, but this patch installs no driver or connection string. Do not use an administrator/service-role connection as the mounted application's default. Pool/driver logs must suppress bind values and raw provider material. Review key custody, rotation, encrypted backup handling, restoration, retention and restricted logout-intent processing before enabling the database control. No enable operation is exposed to the executor.

## Local acceptance

These commands target only the existing approved `tll-stage0-postgres` container and the separately marked `tll_customer_repository` database. They do not accept an endpoint or credentials, create a new container, reset Docker, or touch another database. Run from the repository root:

```sh
# Only on a fresh fixture; refuses an existing database rather than resetting it.
node tests/customer-repository/setup.mjs --create-once
# Repeatable, rollback-only reconstruction of the final migration and ACL attack.
node tests/customer-repository/migration-regression.mjs
# Real independent PostgreSQL connections + actual encrypted repository adapter.
node --experimental-strip-types --test tests/customer-repository/acceptance.test.mjs
node --experimental-strip-types --test tests/customer-token-vault.test.mjs
```

The regression applies the canonical body under non-superuser SESSION AUTHORIZATION, injects inherited schema/table/sequence/function defaults including MAINTAIN, proves private access and temporary authority removed, proves non-superuser operator status/toggling and direct-data denial, rejects session-role impersonation and browser/executor calls, and verifies grant/revoke of the exact executor on a passwordless test LOGIN wholly inside the rollback-only transaction. That LOGIN never commits or becomes available to other sessions. The test rolls everything back. The acceptance fixture retains only synthetic UUIDs and ciphertext; its control is disabled at the end. Tests cover real concurrent claims/subject races, lock-wait expiry, owner denial, stale fences, explicit reauthentication, logout races, lost COMMIT acknowledgements, tampered ciphertext and disabled execution. The local test pool uses a persistent `psql` process per leased connection, so this proves PostgreSQL transactions and adapter ordering; deployment-driver/TLS/pool lifecycle acceptance is still outstanding. No hosted provider, PostgREST, native browser, email, purchase or common-login acceptance is implied.

## Rollback and release gates

Keep the migration unmounted and disabled for review. Before an actual schema install, verify platform metadata/roles, exact source hash, project identity and a restorable backup. A schema inventory is not backup/restore proof. Backups need the encrypted rows **and** independently protected key versions and associated configuration; expired or unavailable keys cannot be reconstructed from SQL. Restore first into an isolated, disabled target and test decryption/ownership without contacting a provider.

If no rows or downstream dependencies have ever been created, a reviewed rollback can drop only the new private schema and its two roles after proving no external memberships/dependencies. Once bindings exist, prefer a forward disable and reconciliation; do not drop reservations, erase evidence, restore broad browser grants or reset fences as an automatic rollback. Upstream Shopify sessions may survive local rollback/logout. Cleanup, retention and the upstream logout flow remain separate reviewed work.

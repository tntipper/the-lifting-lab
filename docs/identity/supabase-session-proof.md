# Disabled staging Supabase session reader

`lib/identity/supabase-session-proof.ts` supplies the connection domain's `currentSession` port. It is **server-only, disabled by default and unmounted**. It adds no route, provider, credential lookup, login, refresh, email, database access or deployment approval. The connection domain still has `liveEnabled:false`.

The trusted server supplies a request-scoped `readAccessToken()` accessor and a staging `sb_publishable_…` key. The accessor is a read-only view of current SSR token material; it must not trust browser-supplied decoded user claims, use a global user client, or silently perform another login/refresh. Reading token material from SSR storage does not authenticate it. No token argument is accepted by `currentSession()`, and no secret/service-role/legacy JWT API key is accepted. Publishable keys identify the application separately from the user's bearer JWT; an opaque key's project cannot be inferred locally, so deployment configuration must bind it and the fixed endpoint. [Supabase API-key model](https://supabase.com/docs/guides/getting-started/api-keys).

## Authority and proof

Before transmission, the reader checks bounded compact JWT syntax, supported HS256/RS256/ES256 headers, the exact staging issuer, authenticated audience/role, nonanonymous flag, user/session UUIDs and times. The audience may be the documented single-entry array. Unsupported critical/key-reference headers fail closed. `jose` decoding is used for **unverified consistency only**; neither a decoded JWT nor a successful local shape check supplies authentication.

The only HTTP operation is `GET https://qdmvngjwkcsilzmqksme.supabase.co/auth/v1/user`, with the exact captured token and publishable key. Its response must confirm the same user UUID, authenticated role/audience and `is_anonymous:false`. Unneeded fields are discarded. The accessor is read again afterward: logout, replacement or even same-session token rotation during verification yields `null`, requiring a fresh verification call. No result is cached or retried. Supabase documents `getUser(jwt)` as a server request suitable for authorization. [getUser reference](https://supabase.com/docs/reference/javascript/auth-getuser).

The inspected upstream Auth revision is `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3`, **not a verified hosted version**. `/user` uses `requireAuthentication`: it parses/verifies the JWT, loads the user, loads a nonempty signed `session_id`, rejects a missing referenced session, and rejects banned users. The response itself does not include a session ID. The reader therefore requires that signed ID locally even though upstream permits legacy tokens with no session ID. It relies on the authenticated handler for the lookup; it does not read `auth.sessions`. [Route binding](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/api.go#L281), [authentication and session lookup](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/auth.go#L20), [user response](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/user.go#L62).

The returned frozen `SupabaseSessionProof` contains only user UUID, session UUID, issuer, audience, `anonymous:false`, authenticated/expiry/checked times in epoch milliseconds. Email, metadata, tokens, headers and raw errors never leave this reader. All failures return `null`; it does not log.

## Authentication recency

`authenticatedAt` is the newest valid timestamp for `password`, `otp`, `magiclink` or `oauth` in the signed token's top-level AMR. Entries require integer seconds, a known ordering before/equal to token issue, and unique methods. Missing/string-only AMR, missing timestamps and malformed lists cannot establish recency. Other methods can coexist but cannot promote the timestamp; supporting another login method requires an explicit policy change. Neither fresh JWT `iat`, `token_refresh`, MFA-only records, recovery, email changes, profile metadata nor user-global `last_sign_in_at` establishes recent sign-in. [Documented JWT/AMR fields](https://supabase.com/docs/guides/auth/jwt-fields).

Upstream generates AMR from that session's method records and each record's `updated_at`, independently of the newly issued token's `iat`. This is why automatic token rotation must preserve the older qualifying authentication time. [Session AMR construction](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/models/sessions.go#L384), [access-token generation](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/tokens/service.go#L671).

A valid session with old authentication still returns a proof. The existing domain requires authentication within five minutes for connection start/callback, and a newly checked current session for refresh/logout. Rejecting all older proofs in the reader would unnecessarily block logout. The regression tests exercise this distinction through the actual domain.

## Transport and acceptance limits

Native Node HTTPS uses a dedicated TLS-verifying agent, fixed GET URL and an honest application User-Agent. It follows no redirects, accepts no caller host/proxy/agent override, and does not decompress. The whole read/verify operation has a five-second default deadline (trusted configuration may choose 50–10,000 ms); response body is bounded to 128 KiB and headers to 16 KiB. It rejects non-200, changed URL, unexpected JSON shape, malformed UTF-8, duplicate representation headers, compression, truncation and oversize. Abort cleanup retains data-free error handling.

Validation: **69 offline tests**, type checking and focused lint pass. Tests include real synthetic JWT signature verification in the fake Auth authority, revoked/nonexistent sessions, mismatched server user/role, fresh-iat/stale-AMR, request token changes, timeout/redaction and an offline probe of the native HTTPS path. No hosted GET or credentials were used. These tests prove local behavior, not tenant session revocation.

Before mounting: verify actual hosted `getUser` succeeds with an authorized synthetic current JWT, then rejects **that exact still-unexpired JWT after server logout**, while a separate remaining session behaves correctly. Check real AMR generation for each supported flow and inspect response shape without retaining private data. Confirm this project's Auth hooks do not rewrite identity/session/AMR semantics. Upstream `/user` checks session existence; this implementation does not independently inspect inactivity/time-box policy fields or guarantee immediate revocation across every platform service. If hosted revocation differs, keep connection activation held and implement a reviewed revocation authority rather than treating a decode or `getClaims` result as equivalent. There remains a normal check-to-action race; durable operation fences/logout generations and repeated domain checks are still required.

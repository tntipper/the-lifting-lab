# Customer OAuth orchestration: admission and remaining gates

This document separates the real Supabase authorization-admission transport from the durable browser orchestration that must precede mounting it. An admission result is a validated upstream URL, **not** an authenticated user, a database commit receipt, permission to redirect, or a completed account connection. All routes below are proposed and remain unmounted. The provider and broker client remain unregistered.

## Configuration boundary

Use one exact server-configured protected staging HTTPS origin. The adapter accepts the existing cart's `https://the-lifting-…-my-lifting-lab-s-projects.vercel.app` host pattern, then matches the returned URL against the exact configured origin. Do not derive it from `Host`, forwarded headers, request input, or a wildcard callback allowlist. Derive the broker browser endpoint `/auth/customer/authorize` and dedicated final application callback `/auth/customer/callback` from that origin. Preserve the existing Shopify callback `/auth/shopify/callback`.

The proposed provider identifier is `custom:tll-staging-subject-broker-v1`; changing it after activation is an identity migration. It is distinct from broker client ID `tll-staging-subject-broker-v1`, Shopify's Confidential client, and the application's own PKCE. The only Supabase issuer is `https://qdmvngjwkcsilzmqksme.supabase.co/auth/v1`. The outer broker callback is that issuer's `/callback`, scope `subject`, response type `code`, method `S256`. The new adapter does not configure any provider or receive the broker client secret.

The pinned Auth source is `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3`, not an assertion about the hosted tenant's running version. [`GetExternalProviderRedirectURL`](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/external.go#L35) creates provider PKCE and flow state before responding. [`LinkIdentity`](https://github.com/supabase/auth/blob/4eee58f296d9698a1c2c0ae14d7a0b379c7622d3/internal/api/identity.go#L156) calls the same allocator and can return JSON with `skip_http_redirect=true`. Thus both GET operations are writes from a recovery perspective.

## Shipped transport boundary

`lib/identity/supabase-authorization-admission.ts` exports `createSupabaseAuthorizationAdmission`. It takes captured, immutable server configuration: `enabled` (false by default), the exact `applicationOrigin`, a staging `publishableKey`, and an optional bounded timeout. A trusted transport override exists for offline tests. With no override it uses real Node HTTPS to the fixed staging issuer with certificate validation, a private agent, response/body/header bounds, and a deadline; no caller can select a host, TLS setting, proxy, redirect policy or cookie jar.

`authorizeSignIn({ applicationPkceChallenge })` sends the application's canonical S256 challenge with Supabase's `s256` method spelling and accepts only the expected 302. `authorizeMigration({ applicationPkceChallenge, accessToken })` uses authenticated GET with `skip_http_redirect=true` and accepts only JSON 200. The latter checks token syntax for header safety; it does not verify the session. The current-session proof, original token match and durable one-use intent remain the caller's mandatory preconditions. An absent migration token fails before dispatch; it cannot fall back to sign-in.

The result contains only a normalized `authorizationUrl` and `authorizationQuery` for the validated outer protocol tuple. Duplicate query/header values, wrong origins/paths/client/callback/scope/state/PKCE, credential/error parameters, malformed representations and expanded scope fail closed. The exact independently generated outer challenge must differ from the application challenge. Harmless unknown OAuth/JSON extensions are ignored and removed from the result; expected forwarded `redirect_to`, `provider`, `scopes` and `skip_http_redirect` fields, when present, must match the owned request. No unknown field becomes a target, mode, proof or browser output. Durable registration binds this normalized security tuple to the original intent, rather than treating unrecognized extension text as authority.

The adapter captures a URL without following it. It never returns response bodies/headers/cookies, persists a session or logs provider errors. Exceptions expose only fixed `SUPABASE_ADMISSION_HELD` and `not_attempted` or `uncertain`; raw errors are not retained as causes. Once transport begins, even a definite error response is held as uncertain because upstream state may exist. The module has no cache or automatic retry.

## Intended browser and machine surfaces

| Proposed surface | Authority and sequence |
| --- | --- |
| Protected Next `POST /auth/customer/start` | Exact origin and CSRF checks; explicit sign-in or authenticated migration; current request-scoped session proof; fresh HttpOnly/Secure/SameSite browser transaction secret; durable encrypted intent and one-use admission claim; then one Supabase admission request. |
| Protected Next `GET /auth/customer/authorize` | Exact returned outer query, original browser secret and acknowledged outer registration must all match. Reject a direct provider URL, foreign browser or consumed transaction before Shopify authorization. Commit independent Shopify state/nonce/PKCE before redirect. |
| Protected Next `GET /auth/shopify/callback` | Original browser and inner state; one-use durable code-exchange claim; real Confidential exchange, signature/issuer/audience/nonce/PKCE validation; encrypted provisional tokens and verified-subject receipt. Recheck original migration session before committing broker readiness. |
| Separate staging Edge `POST` token endpoint | Fixed Confidential Basic client, exact code/redirect/S256; narrow database operation consumes code and creates one-use broker-only bearer. No Shopify secret or provisional vault key. |
| Separate staging Edge `GET` userinfo endpoint | Only the broker bearer; transaction/generation/readiness deadline checks; commit consumption before returning the reserved opaque `sub`. No customer profile, email, Shopify tokens or refresh token. |
| Protected Next `GET /auth/customer/callback` | Original browser transaction and committed outer flow; one-use application PKCE exchange in isolated temporary storage; authoritative final Supabase user/identity verification; durable reconciliation acknowledgement; sanitized SSR cookie release last. |
| Protected Next `POST` cancellation/logout endpoints | CSRF/origin and current browser/owner authority; durable generation changes and access tombstones before upstream logout. Track provider logout and cleanup independently until acknowledged. |

Next routes use explicit `no-store`, bounded inputs and fixed redirects, with no credential-bearing telemetry. The [Next 15 route guide](https://nextjs.org/docs/15/app/getting-started/route-handlers-and-middleware) defines route handlers and caching behavior; there are no new route files in this slice. Browser endpoints remain behind preview protection. Machine functions need their own protocol authentication and reviewed per-function JWT setting; they must not contain a Vercel bypass key or depend on a browser SSO cookie. Their mounting, permissions and platform-provided credentials require a separate review.

## Distinct durable stores

The existing customer repository owns UUID-bound connections. It must not be weakened to represent a customer who does not yet have a Supabase UUID. The broker repository owns outer registration, one-use readiness/code/bearer state and private stable-subject reservation. It stores only minimal trusted Shopify proof metadata and any pending migration target; it cannot decrypt inner tokens or infer a completed account link. Its `claimReadiness` and `finishReadiness` intentionally share the same operation ID.

A separate provisional orchestration repository is still required. Before any upstream admission request it must durably store a never-reused transaction ID, hash of the browser secret, immutable mode, exact configuration hash, attempt deadline, application PKCE material and, for migration, original verified UUID/session plus the access-token hash. Application PKCE verifier, inner state/nonce/verifier, temporary final session and Shopify token bundle need authenticated encryption with a distinct provisional purpose and AAD bound to transaction/configuration/generation. A new sign-in has no target UUID. Do not use the UUID connection vault's owner AAD with an invented owner.

Its transitions must use database time, one-use claims, immutable request bindings, cancellation generations, bounded retention and acknowledged commits. Public receipt IDs are locators only; the trusted verifier must actually validate and commit the evidence. Code strings, tokens, cookie secrets and raw provider failures do not belong in operation logs. The transport adapter will not accept a `verified:true` flag, pretend an in-memory map is durable, or manufacture an intent receipt.

## Admission sequencing and recovery

1. Commit the encrypted provisional intent and atomically claim `prepared -> admission_inflight` once. A failed or lost claim acknowledgement prevents HTTP dispatch. The migration's independently verified request-scoped access token must still match its retained original session and token hash at this point. Never accept a token or target UUID from form/query fields.
2. Call the adapter once with the retained application challenge. Sign-in uses the fixed `/authorize` endpoint and inspects its 302 `Location`; migration uses the fixed `/user/identities/authorize` endpoint with the exact bearer and `skip_http_redirect=true`, accepting a 200 JSON `url`. Never follow either response or forward the bearer to the broker.
3. Validate the returned exact broker URL, client, callback, scope, UUID state and independent outer S256. Commit the original response binding to the provisional intent and register it with the broker repository before any browser redirect. The two-store bridge must be recoverable by immutable transaction/binding reads; an application cookie or random receipt alone cannot substitute for that commit.
4. If either response or commit is lost, remain held. Do not repeat the Supabase GET, regenerate the application verifier, restore a consumed code, or clear an uncertain claim. An upstream flow whose URL was never acknowledged is never broker-admitted. A known outer flow is quarantined/cancelled by its immutable browser/outer binding. A database read may establish whether an acknowledged transition exists; it must not turn uncertainty into a second upstream attempt.
5. A fresh explicit browser transaction is possible only after the prior local generation is durably fenced. Its IDs and PKCE are new. Keep the previous held record until the retention/reconciliation policy permits cleanup. Reusing an intent ID, operation ID for another transition, state, code or bearer is forbidden.

The adapter's `not_attempted` error means this call never entered transport. It does not erase any earlier uncertainty for the transaction. Every failure after dispatch, including a provider rejection or malformed response, is conservatively `uncertain`: flow allocation may already have happened. No adapter path retries. Even a successful adapter return requires the durable commit and registration steps above before use.

## Inner proof, final reconciliation and cookie release

The provisional Shopify callback claims the code exchange before sending it. An uncertain Shopify exchange remains held and cannot be retried; a browser returning to an old callback cannot reclaim it. Successful token verification produces an encrypted bundle and narrow receipt tied to this transaction and exact shop/issuer/subject. All three PKCE challenges—application, outer broker, inner Shopify—must be different. The callback rechecks the current original migration session, including revocation and authentication recency, before broker readiness.

Readiness lasts at most five seconds from those checks. Token and userinfo transitions enforce the same deadline, even though the opaque bearer has a nominal 60-second lifetime. Edge cannot restamp proof time. This bounds an unrelated upstream revocation race; it is not synchronous cross-provider revocation and cold starts can legitimately hold a flow.

The final callback must not use the application's generic callback or an SDK instance that writes SSR cookies during exchange. First durably claim the final application exchange; use a request-scoped isolated SDK storage/cookie sink with no browser writes and no automatic background refresh. Verify the resulting access token against the actual Supabase user endpoint and require the exact configured broker identity and reserved stable provider subject. In Auth identity JSON, `id` is the provider subject and `identity_id` is the identity-row UUID; email and mutable metadata are never identity keys. For migration the final user UUID must equal the original target UUID; its new session ID need not equal the original session ID. For sign-in only this authoritative final identity supplies the UUID.

A separately reviewed reconciliation operation must join the consumed broker reservation, matching provisional verified receipt/encrypted tokens and final authoritative UUID without direct `auth.identities` writes. It must atomically reserve the canonical binding and produce a durable promotion result, or leave a conflict held. An uncertain final exchange or promotion cannot be repaired by creating another auth user, email matching, replaying the code or reassignment. Keep isolated session material encrypted and unavailable until the reconciliation read confirms the exact committed result.

Only an acknowledged promotion permits sanitized SSR persistence, with `provider_token` and `provider_refresh_token` removed. The broker bearer should already be consumed at userinfo; sanitization is additional protection. Cookie delivery itself can be lost after promotion, so recovery must prove the current browser and durable final result before a reviewed resumable delivery step, or fence the isolated session and require explicit reauthentication. It must not repeat the final token exchange.

## Activation gates

This transport slice does not satisfy durable intent storage, provisional encryption, route CSRF/browser binding, final exchange/reconciliation, owner-wide cancellation/logout, retention or actual provider interoperability. Mounting requires those implementations and independent tests of lost responses/commits, concurrent starts, account switching, direct/transplanted flows rejected before GoTrue's link side effect, no-email creation, legacy UUID/data/reward preservation, spent-bearer sanitization and cleanup. Keep enabled hosting and production acceptance separate from local injected-transport checks.

Local validation uses `tests/supabase-authorization-admission.test.mjs`: request/response shape, bearer confinement, extension projection, configuration capture, input and destination rejection, duplicate/encoding/framing limits, no-retry uncertainty, timeout/late completion, and the actual Node adapter through an offline HTTPS boundary probe. The probe intercepts `node:https`; it checks TLS and no-redirect construction without opening a socket. It does not establish real provider reachability, durable intent or hosted acceptance.

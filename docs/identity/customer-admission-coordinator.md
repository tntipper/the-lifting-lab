# Disabled customer authorization admission coordinator

`lib/identity/customer-admission-coordinator.ts` joins the actual encrypted 008 provisional repository, Supabase authorization-admission transport and current-session reader. It is unmounted and disabled by default. Its only successful output is a **server-private admission candidate**. The separate recoverable 008-to-007 registration bridge must acknowledge the exact outer transaction before a browser may receive that URL. This slice neither implements that bridge nor authorizes a redirect, authenticated browser, identity promotion or login completion.

The constructor captures one exact approved staging origin, publishable key, dedicated bounded idle-client pool, independently held provisional vault, and request-scoped SSR access-token accessor. It constructs the actual adapters internally; it accepts no caller-provided repository implementation, `currentSession`, verified flag, target UUID or admission response. Trusted HTTP transports and a clock can be injected for offline tests. The pool must bound acquisition and use the isolated provisional executor identity; 008 bounds SQL/lock/idle-transaction waits. No environment loading, LOGIN provisioning, routes, SDK storage, cookies or hosted calls occur at import. `syntheticExecution: true` enables local fixtures only; `liveEnabled: true` always fails shut.

## Server authority and sequence

`startSignIn({ browserSecret })` and `startMigration({ browserSecret })` take only a canonical 32-byte base64url secret extracted by a trusted server handler from a **server-created** HttpOnly transaction cookie. It is not a client-selected owner or a form/query parameter. A future route must supply exact-origin/CSRF protection and secure cookie issuance/extraction; this unmounted primitive does not prove those controls. Each request-scoped coordinator instance accepts at most one start, including concurrent calls. Reconstructing an instance and calling start is not recovery: a fresh explicit browser transaction requires separately acknowledged fencing of its predecessor and a new cookie. That route-level policy remains an activation gate.

Before preparing, the coordinator captures the browser hash and generates one transaction UUID, two operation UUIDs and independent 32-byte application PKCE verifier. Configuration, mode, challenge, creation time and five-minute deadline are immutable. It constructs metadata before the first database call so a lost preparation acknowledgement still leaves the original quarantine binding. Sign-in has no user UUID. The verifier is sealed by the actual 008 vault adapter and is absent from every coordinator result.

Migration first verifies the SSR token using the unchanged actual session reader and authenticated fixed-project `GET /user`. The token is reread by that reader before returning proof. Only its verified UUID/session and the exact token hash enter the immutable original-owner metadata. After preparing, a second actual reader call verifies the same retained token, current session and original UUID/session. This catches revocation and account/token switching across database waits. Proof must retain a login/reauthentication time within five minutes; refreshed JWT issue time is not substituted. The newest proof must be no more than five seconds old, unexpired and unchanged when admission is dispatched. After the acknowledged claim, a bounded SSR token reread immediately precedes the link request. This is a bounded revocation window, not synchronous cross-service revocation; a revocation after the last check still requires later broker/callback gates.

The ordered write path is:

1. Acknowledge 008 `prepare`, with encrypted verifier and immutable intent.
2. Acknowledge `claimAdmission`, passing actual migration proof or null for sign-in. The claim and later finish share the original claim operation UUID.
3. Dispatch exactly one real admission GET with the retained application challenge. Sign-in uses the fixed Supabase authorize endpoint; migration uses its fixed authenticated identities endpoint and the exact verified bearer. Redirects are never followed.
4. Acknowledge `finishAdmission` with the normalized broker URL/query and exact original binding, fence and generation.
5. Return the private candidate, immutable original binding and claim metadata. A future 007 bridge is still required before any browser release.

Supabase's pinned Auth source `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3` allocates provider flow state during both GET paths; the source links and expected 302/200 response details remain in [the orchestration design](customer-oauth-orchestration.md). A GET is therefore a consuming action for this coordinator. That source pin is not evidence of the hosted tenant's running version or interoperability.

## Held outcomes and inspection

Any failure once the immutable intent exists, including missing or rejected prepare/claim/finish acknowledgement, invalid upstream response, timeout or switched migration session, attempts `holdOperation` on that same original binding. The acknowledged claim fence/generation are included only when known. Preparation and claim operation IDs are captured once, never replaced during recovery. Known holds destroy the encrypted verifier; a lost preparation acknowledgement can create an exact tombstone before a late writer. If the hold acknowledgement is also lost, the result remains held with `quarantine: 'unacknowledged'` and the original private binding. It never exposes the candidate URL or raw errors, tokens, verifier, account details or provider failures.

Failures before an intent exists use the same generic held status with null binding and `quarantine: 'not_required'`. This means no durable intent was attempted by that call, not that an earlier transaction has been cleared. The coordinator has no retries, whole-function retry wrapper or reclaim operation. One-use admission authority resides in PostgreSQL, not a local flag or metadata receipt; the local single-use guard only prevents accidental reentry of the same request instance.

`inspect({ binding, browserSecret })` verifies the original browser hash and queries only the exact immutable binding. It returns state, observation time and expiry, never an outer tuple, URL, verifier, credentials, session proof or claim fence. Even an observed `admitted` row after a lost finish acknowledgement cannot authorize another GET or browser redirect. Inspection performs no dispatch or state restoration. Unknown hold outcomes need separately reviewed fencing/recovery; metadata alone cannot complete them.

Run `node --experimental-strip-types --test tests/admission-coordinator/acceptance.test.mjs` only after the existing marked `tll_provisional_repository` fixture is released by its owner. This suite uses the actual 008 PostgreSQL function/vault/adapter plus actual session/admission adapters, signed synthetic HTTP responses, revocation, session switching, concurrent reentry, encrypted PKCE inspection and SQL/COMMIT acknowledgement faults. It neither creates a fixture nor contacts Supabase. It disables/empties the synthetic fixture on completion. Do not run it concurrently with the repository acceptance suite.

The candidate provider remains unregistered, every route remains unmounted, and runtime activation is excluded. The 007 bridge, protected browser entry/cookie binding, authenticated machine endpoints, provisional Shopify exchange, final exchange orchestration, reconciliation, cancellation/logout propagation, retention and controlled provider interoperability remain separate gates. This coordinator does not call the final exchange adapter, inspect email or mutable metadata, modify `auth.identities`, or release SSR cookies.

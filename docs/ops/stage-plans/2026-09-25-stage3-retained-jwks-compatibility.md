# Stage 3: exact retained JWKS compatibility, disabled preparation

The 25 September [official staging read](../evidence/2026-09-25-stage3-provider-safe-held-read-v1.md) established that the custom OAuth2 provider is disabled and retains one known JWKS address. The previous two-field normalization failed; its consumed journal and strict acceptance rule remain historical evidence, not a workflow to retry.

The broker returns an opaque access token and obtains `sub` from userinfo, without issuing an ID token. In the pinned published Supabase Auth source, the [OAuth2 provider constructor](https://github.com/supabase/auth/blob/ce9a8eee0cc042be8c7a42981a7ddae631e41d91/internal/api/external.go#L3277-L3335) does not receive JWKS, and the [Admin update handler](https://github.com/supabase/auth/blob/ce9a8eee0cc042be8c7a42981a7ddae631e41d91/internal/api/custom_oauth_admin.go#L629-L634) ignores an empty JWKS update. This supports retaining the exact existing value in **disabled source preparation**. The hosted Supabase binary and a real sign-in journey remain unproven.

The replacement future-rotation contract pins the observed address exactly, requires provider type OAuth2, disabled state, PKCE, expected client/endpoints, no issuer/discovery document and the existing no-secret/no-enabled-control preflight. It omits `jwks_uri` from the future update payload and verifies that the exact address is still present in the update response and separate readback. Unknown, blank or near-match addresses stop before credential generation. Uncertain updates still retain staged host values and require reconciliation; consumed journals are never replayed.

The hosted-baseline observation is version 2. It reports only whether the address exactly matches and whether a discovery document is present; arbitrary or missing addresses and any discovery document produce `provider_jwks_drift`. The strict session projection independently reconstructs that reason and rejects version 1 receipts. The original normalization contract stays disabled and unchanged.

This change is local preparation only. No provider, secret, database, Vercel setting or application flag is altered. Before any hosted rotation: independently review the exact committed diff and a new one-run plan; refresh the official staging baseline and protected Preview identity; confirm the real hosted OAuth2 behavior; verify all launchers remain disabled; then seek separate action-time approval. Keep account/cart activation on HOLD until the complete owner-email sign-in journey is proven without purchase.

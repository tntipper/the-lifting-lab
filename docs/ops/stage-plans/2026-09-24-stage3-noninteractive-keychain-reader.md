# Stage 3 noninteractive legacy Keychain reader — disabled implementation plan

## Outcome and acceptance

Replace the prompt-capable `/usr/bin/security -w` credential acquisition path with a narrowly scoped, bounded native reader for the Mac's existing file-based `login` keychain. A required authentication UI must produce a fixed stop category before provider intent or mutation. This is a prevention design for the still-open credential incident, **not** proof of its historical cause.

The first work unit is source, an offline build and injected tests only. Acceptance for that unit is a compiled disabled helper; tests for exact selectors, noninteractive-setting failure, access status categories, invalid data, partial output and restoration failure; a reviewed source/binary build recipe; no real-item access, ACL change, hosted request or consumed journal. A parent-enforced timeout belongs to the later launcher-integration gate; this disabled reader is not connected to a parent process yet. Qualifying runtime behavior with a disposable non-secret item is a separate later gate.

## Current evidence and exclusions

Main integration branch starts after the readiness V1 PASS evidence commit `47c002c`. The local readiness receipt is terminal and cannot be replayed. Both provider-mutation receipts remain absent; the readiness and provider launchers are disabled. An independent incident review found the prior storage mistakes but could not classify the earlier exact-helper failure. Current `/usr/bin/security` command/selector/environment/timeout did not change before the PASS, so exit categorization alone is not a repair.

Do not read the three real Keychain values, create or rotate credentials, change any real-item ACL, lock or alter the login keychain, call provider APIs, push, deploy, purchase, message customers, or invoke any provider launcher in this disabled work unit. Do not turn a native reader on merely because it compiles. Preserve all existing one-use receipts and unrelated untracked paths.

## API and implementation boundary

The current items appear in Keychain Access under the file-based `login` keychain. Apple distinguishes this legacy store from the data-protection keychain; `kSecUseNoAuthenticationUI`/`LAContext.interactionNotAllowed` alone may still permit UI for legacy items. For this legacy path, the reader must save the prior `SecKeychainGetUserInteractionAllowed` value, require `SecKeychainSetUserInteractionAllowed(false)` before `SecItemCopyMatching`, and restore the prior value before releasing output. Pin the intended keychain with `kSecMatchSearchList`, exact generic-password class, service and account; request one data result. Do not opt into `kSecUseDataProtectionKeychain` or synchronizable items. The legacy interaction switch is deprecated but present in the installed macOS SDK; qualify it on this Mac before real use. Apple sources: [Keychain interaction control](https://developer.apple.com/documentation/security/seckeychainsetuserinteractionallowed%28_%3A%29), [legacy versus data-protection keychains](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains), and local SDK `Security.framework/Headers/SecItem.h` near `kSecUseNoAuthenticationUI`.

The helper must have a fixed three-selector allowlist, no arbitrary item name or keychain path from untrusted caller, no logs or raw OSStatus in output, no UI fallback, no retry, and a fixed maximum value size. The later launcher integration must enforce a parent deadline before real-item use. It must classify interaction-required, authentication failure, item missing, keychain unavailable, configuration failure, decode failure, cancellation and unknown errors separately; return a fixed category for restoration or output failure. Credential bytes may travel only through the reviewed launcher's private pipe. Use one reference-owned mutable secret buffer; Swift copy-on-write arrays can leave an unwiped alias. Wipe that actual read-path buffer on every outcome and test its post-run contents. Promptly release framework-owned results; do not claim to erase immutable framework allocations. A new executable will not inherit `/usr/bin/security`'s ACL authorization.

Permitted repository files for this disabled unit: this stage plan, one native reader source, a reproducible fixed-path build/check script, isolated injected tests, source pins/manifest updates, incident evidence and `.agent/HANDOVER.md`. New source must remain disconnected from live launchers until qualification and a separate integration plan. No binary or secret belongs in Git.

## Execution and failure controls

1. Verify branch, HEAD, working tree, disabled boundaries, receipt state and Mac toolchain. Read Apple/local SDK API contracts before coding. Keep existing staging integration source untouched outside the allowed files.
2. Implement a pure status/selector/access sequence that can be tested with injected Security calls. Build from an immutable private snapshot of the exact source bytes; verify the source still matches that snapshot before publishing the binary. Record source and binary hashes, architecture and signing identity without running it against real items. Never label a binary with a source hash computed only after compilation.
3. Run injected offline cases for all categories, denied interaction, failed setting/restoration, invalid or oversized data, partial write and cleanup. Tests must prove no credential output before all access and restoration checks succeed and prove the actual reference-owned read buffer is wiped. Isolate and test the pipe write loop with injected partial, zero and failed writes; a partial write failure may already have sent bytes into the launcher's private pipe, so the parent must discard and wipe all output on every nonzero child exit. Run appropriate type/build, focused tests, activation-manifest and live-boundary checks while every native gate is disabled.
4. Independently review the disabled diff, deprecation/legacy-keychain compatibility, output boundary, build identity, failure mapping and test isolation. Correct defects and reverify before committing. Update incident and handover with precise remaining uncertainty.
5. Later, under a separately reviewed qualification plan and action-time approval, use only an isolated disposable keychain with non-secret fixtures to test allowed, denied, locked and missing-item behavior. Never lock the real login keychain or grant new real-item access as part of that qualification. A separate exact-item ACL plan and approval would be needed if the compiled reader is ever used for real items.

Stop on an unexpected Keychain prompt, real-item read, source/build mismatch, inability to suppress UI, ambiguous result, cleanup/restoration failure, or test access to a live provider launcher. Preserve evidence and do not retry by creating a new generation. Provider mutation remains HOLD until this alternative is qualified, independently accepted, freshly authenticated against hosted staging, and separately approved.

# Stage 3 disposable Keychain qualification — proposed next gate

## Outcome and boundary

Qualify the reviewed native reader's real macOS Security.framework interaction behavior using a newly created, disposable file-based keychain containing only synthetic, non-secret text. Establish whether allowed, denied, missing and locked reads return fixed categories without presenting an authentication prompt or reaching any real credential. This does **not** qualify access to the existing login keychain or close the provider incident.

The one-use readiness receipt is consumed; provider-mutation receipts remain absent. ## Proposed one-run sequence after approval

Every native setup, read and cleanup process must save the prior legacy interaction setting, successfully set `SecKeychainSetUserInteractionAllowed(false)` before a potentially interactive operation, and restore the prior value on normal completion. Use Security.framework `SecKeychainCreate` with `promptUser=false` and a non-null in-memory synthetic password to create one file-based keychain **outside** the user's login-keychain path, under a new owner-only directory. The filename must not resemble the special login or System keychains. Capture default-keychain identity and search-list metadata before creation and immediately afterward; stop before reads if either changed. Never call a search-list setter.

Create two synthetic generic-password items with explicit access controls through an API accepting `SecAccessRef`, such as `SecKeychainItemCreateFromContent`. Trust the exact compiled fixture-reader identity for the allowed item; trust no applications for the denied item. Verify the intended access metadata before either read. Use a third selector that is absent by design. With the fixture reader constrained to this exact temporary keychain, allow at most four reads: unlocked allowed, unlocked missing, unlocked denied/interaction-required, and locked allowed. Check successful output against the expected synthetic value inside the private parent pipe before wiping it; exit status alone is insufficient. Bound every child by a parent deadline and discard/wipe all captured bytes on a nonzero exit. `SecKeychainLock`/explicit-password `SecKeychainUnlock` apply only to this disposable keychain. `promptUser=false` suppresses only the creation dialog; the interaction switch and deadline cover the remaining native operations. An unexpected macOS dialog is a stop condition, never something to answer or accept.

After the one run, stop regardless of outcome. Reserve a bounded, journaled cleanup phase for known failures after the child has exited. Recheck the particular default-keychain identity, search-list metadata and fixture path/reference; do not claim all login-keychain state was observed. Delete only a verified fixture reference/path identity with `SecKeychainDelete`, then verify the returned path and any resulting fixture files are gone. Do not restore an old search-list snapshot over concurrent changes. If a child times out or its effects are uncertain, stop and preserve the private fixture for separate read-only reconciliation before any further mutation. If cleanup fails, preserve the private file and record HOLD; never delete by an unverified path or run a second test to diagnose. Disarm any local fixture gate and record a secret-free receipt, review outcome, and update incident evidence and `.agent/HANDOVER.md`.

## Stop conditions and remaining gates

Stop before reading on any path/selector mismatch, missing private-directory ownership or mode, source/binary hash mismatch, unexpected UI, blocked child beyond deadline, unexpected return value, changed default keychain search list, cleanup failure or receipt replay. No production provider, Vercel, Supabase, Shopify, real Keychain item, production deployment, purchase or customer message is in scope. Even a full fixture PASS only qualifies the disposable setup; exact real-item ACL access, launcher integration and parent failure behavior need separate reviewed gates and explicit approval before provider mutation.

# Stage 3 local credential-readiness window (disabled design)

## Outcome and exclusion

Prove whether the exact provider-normalization Keychain helper can read **all three** required local credentials in launcher order, without revealing values or consuming either provider-mutation journal. This is a read-only local diagnostic. Success is a terminal private receipt at the final read phase with overall PASS, an absolute deadline and no value in output; the reviewed source and tests establish selector order and exact invocation parameters. A HOLD identifies the first failing read phase and fixed helper exit category; it does not trigger a retry or provider mutation.

No Supabase/Vercel network request, new credential, Keychain permission change, source push, deployment, provider change, account/cart activation, purchase or customer message is in scope. The readiness result alone does not authorize the provider change or close the incident's still-unproved root cause.

## Allowed disabled implementation

Add a dedicated `scripts/staging-provider-credential-readiness-live-launcher.mjs` with a false native gate, a separate `scripts/staging-provider-credential-readiness-phase-journal.mjs`, an injected `scripts/staging-provider-credential-readiness-native.mjs` adapter and focused offline tests, activation-manifest source pins and this plan/handover. The launcher calls the same bundled Python executable, `-I -S` arguments, helper path, working directory, PATH/LANG-only environment, ignored stdin, 15-second parent process deadline and 4,097-byte output ceiling as the provider-normalization launcher. Helper's own `/usr/bin/security` timeout remains 10 seconds. It must create its own exclusive mode-0600 private phase record **before** any Keychain call, advance through three selectors in order, store a 50-second absolute deadline plus phase deadlines, and reserve the full 15-second child limit before each read. Mark any exceeded deadline HOLD; synchronous filesystem finalization may complete after the deadline, so monitor the receipt and never infer progress from silence. Keep both provider-mutation journals absent and untouched. Capture, validate and wipe every owned output buffer; report only fixed categories and rounded elapsed time, never credentials or raw stderr. Fail closed on a consumed/malformed/symlinked receipt, unexpected helper exit, timeout, invalid output, cleanup error or deadline breach. No automatic retries.

Offline tests must inject a fake child process and private temporary journal. They must verify ordering, timing, categorical failures, zero secret output, buffer wiping, mode, replay refusal, and that neither provider-mutation journal is touched. Do not import or invoke the live launcher from ordinary tests. Its orchestration should be injected from a separate pure module where needed. Run ordinary tests only while every native gate remains false. Regenerate the activation manifest and independently review the exact disabled diff, including its journal and all native boundaries.

## Later action gate

After disabled implementation and independent review, obtain a fresh owner approval for a **single local credential-readiness window**. In a local-only sibling checkout, enable only the readiness and exact-helper gates with a reviewed minimal diff and generated manifest; provider-mutation gates stay false. Verify the new private readiness receipt is absent, current credential selectors and Keychain ACLs, then invoke the readiness launcher **once**. Immediately disarm, preserve its terminal receipt, reconcile access categorically and update the incident. A PASS is evidence only for that bounded window; a HOLD blocks the provider stage and is not retried. Provider normalization requires a distinct later hosted baseline, exact arming review and action-time approval.

# Stage 3 access-route reassessment — 25 September

**Decision: keep provider mutation and account/cart activation on HOLD. Do not start the proposed disposable Keychain qualification as the default next action.** This is a planning correction, not a new authorisation or a code change.

The current one-shot provider launcher requires three saved credentials before it reads the staging state: Supabase CLI, Vercel API and the protected Preview bypass. Its Python helper calls `/usr/bin/security` separately for each. A prior attempt failed at this access step; a later one-use check read all three, but did not explain the intermittent failure. The alternative Swift reader is disabled and has passed only injected tests. The synthetic fixture that was later cleaned up was for a different operation. Both provider-mutation journals are absent and all provider controls remain disabled. See [gate reassessment](2026-09-25-stage3-provider-gate-reassessment.md) and [credential incident](2026-09-24-stage3-provider-credential-storage-incident.md).

The proposed disposable reader qualification would show only how a *new synthetic item* behaves with a *different executable identity and access rule*. Its own plan says that even a PASS would not qualify access to the three existing items or close the provider incident. It also requires another Keychain creation, one-use journal, cleanup and separate parent integration, after the previous fixture needed a long recovery. That is too much cost and local-system risk for the proof it yields. Preserve the disabled Swift source as an option; do not discard or arm it.

## Shortest evidence-led route

1. Restore a working signed-in read-only browser connection and identify the exact **staging** Supabase provider and Vercel Preview state. The two browser-control attempts in this continuation timed out before returning a page. Do not infer that the Mac is locked or that the hosted state is unchanged. If the UI is unavailable, work on independent launch tasks rather than consuming another credential window.
2. Inspect whether the Supabase dashboard offers a bounded change of only `enabled` and `jwks_uri`, with a full-field before/after read and a reliable way to detect any collateral field change. If that is demonstrable, prepare a one-attempt dashboard procedure for independent review. If not, assess a smaller **Supabase-only** official API operation that reads the full provider, sends exactly `{enabled:false,jwks_uri:''}` once, and reads it back; obtain a separate read-only Preview check before activation. Either route needs fresh evidence, a reviewed failure/recovery plan and action-time owner approval before mutation.
3. Do not weaken the current launcher in place to bypass its Preview safety checks. If a smaller provider-only operation is chosen, build it as a separate disabled, narrowly scoped slice. Prove no customer/cart control can activate, no other provider field changes, and any uncertain update stops without retry. Continue with the existing full integration checks before enabling sign-in.

This route separates the safe act of *disabling an unused staging provider* from the later decision to activate customer sign-in. It does not claim that browser editing is safe, that existing tokens work, or that the provider was changed. The older nine-gate launcher remains disabled and must not be reused without a newly reviewed plan.

**Status:** customer journey untested; staging contained. This review is read-only. It does not authorise another activation. Current disabled source is `4495cb77021e69fe683c016216e75af79ccf66e0`; preserve the armed v6 commit `2e1a3b270cb2a59206b2ebf68b7f267998c1ab4c` and all consumed records.

The restricted-connection check completed the customer and cart roles, then failed connecting the broker role on its **second** attempt at `2026-09-27T20:14:58.843Z`. The private diagnostic is `../implementation-state/staging/tll-generation-23-restricted-connections-v6.json` (`HOLD`, `correct_roles`, `broker`, `connect_retry`). This was not a role-proof deadline: it failed approximately 62 seconds into a 180-second correct-role allowance. V5 passed this same connection stage. Neither fact establishes why the broker connection failed.

## Why the run could not diagnose itself

The actual application database transport, `lib/server/staging-postgres.ts`, deliberately converts driver connection errors, its four-second connection-acquisition timeout and a failed post-connect transaction-state check to the same generic `Staging database unavailable` error. The verifier, `scripts/staging-generation-6-connection-verifier.mjs`, discards the first connection error, waits 16 seconds, then also replaces the second error with only a role/check label. The Generation 23 wrapper saves that label but omits even the verifier's safe `purposesPassed` count. Query-denial SQLSTATE handling does not cover a connection failure. This is a **confirmed defect in private test diagnostics**. It prevents a defensible claim that the v6 failure was an incorrect password, Supavisor cache, connection limit, network/TLS problem, timeout or client-state mismatch.

**New read-only log evidence:** The existing Supabase CLI access successfully queried `supavisor_logs` via the official Management API for `20:13–20:16 UTC`. The exact v6 broker retry produced `password authentication failed` and SQLSTATE `28P01` at `20:14:58.797–20:14:59.299 UTC`. The customer role had the same initial password rejection at `20:13:57.738` and authenticated after a retry at `20:14:15.025–20:14:15.036`; cart was rejected at `20:14:16.146` and authenticated at `20:14:34.650–20:14:34.658`. The bounded 24-row log response showed no circuit-breaker or client-limit event. The log query did not expose or save raw credentials. These events prove the immediate broker failure was **database authentication**, not a Vercel, browser, checkout or provider fault. They strongly support delayed Supavisor recognition of fresh role passwords, because two other newly changed roles were rejected and then worked after the wait. They do **not** prove the broker password itself was correct, because no successful direct broker connection was made before retirement.

Every supervised run changes passwords on five roles and immediately connects through Supabase's shared transaction pooler at port 6543. Supabase documents a short credential cache after password changes: fresh correct credentials can be rejected, usually resolving after a reconnect in around 15 seconds; occasional retries can fail for longer. The current runtime has a three-second driver timeout and four-second acquisition timeout, and the verifier permits only one 16-second wait/retry. Repeated failed authentication may also trigger a pooler circuit breaker for up to two minutes. The v6 logs point to password/cache handling as the priority, not to a general site defect.

Official references: [Supabase password-rotation guidance](https://supabase.com/docs/guides/troubleshooting/supavisor-error-password-authentication-failed-after-password-rotation), [Supabase circuit-breaker guidance](https://supabase.com/docs/guides/troubleshooting/supavisor-error-circuit-breaker-open-after-password-rotation-0fdb72), [Supavisor log guidance](https://supabase.com/docs/guides/database/supavisor), [Supabase connection limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits).

## The larger process failure

V4, V5 and V6 stopped at **different** real integration points: website/source assumptions, an encrypted Vercel setting acknowledgement, then a broker database connection. Each correction passed local tests, but those tests replaced the exact hosted component that failed next. The local composite test substitutes Docker Postgres for the real Supavisor connection wrapper. Thousands of local passes therefore do not prove the complete hosted customer journey. The safety controls and one-use records helped contain each failure, but the repeated full-window setup is an expensive way to discover a single interface mismatch. The independent Astra review agrees that the diagnostic loss and test-boundary mismatch are systemic process faults, not evidence of a single permanent Supabase outage.

## Next action before any more paid supervised attempt

1. Stop rotating the same five role passwords immediately before every customer-flow attempt. Choose stable staging-only, least-privilege credentials with a separately verified login and a clean rollback, or create fresh role names alongside the old ones as Supabase advises for password changes. Verify direct connection first and pooler connection only after convergence; do not proceed to customer activation until both pass. Keep explicit OFF controls. Separate deliberate wrong-password security probes from the customer-flow window to avoid triggering the pooler's circuit breaker.
2. Add a **private, allow-listed connection diagnostic** at the real runtime boundary: operation (`driver_connect`, `acquire_deadline`, `postconnect_state`, `closed`), safe SQLSTATE or network code, attempt and elapsed-time bucket. Never expose raw error text, connection string, password or SQL result to customer routes or public logs. Carry this safe category through the verifier to the one-use record. Prove it with the real runtime and verifier while replacing only the database driver, including timeout and cancellation cases.
3. Rehearse the **actual assembled route** once with simulated external responses at the network boundary, not replacement business logic. Then run one protected staging customer journey: owner sign-in, orders, guest cart transfer, exact item/price, GET-only checkout page and logout; verify final OFF/retired state. Failures during that journey are collected as findings when safe, while an uncertain activation or payment risk still causes immediate containment.

No engineer can guarantee a 100% pass through third-party services or an owner sign-in code. The gate for another run should instead be concrete: the failure cause can be observed, the full assembled path has passed its rehearsal, credentials and connection method have passed a separate readiness check, the owner is present, and shutdown has been proved. Do not issue another generation merely to consume a new record.

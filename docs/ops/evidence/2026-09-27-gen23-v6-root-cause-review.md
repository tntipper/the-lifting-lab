## Why the run could not diagnose itself

The actual application database transport, `lib/server/staging-postgres.ts`, deliberately converts driver connection errors, its four-second connection-acquisition timeout and a failed post-connect transaction-state check to the same generic `Staging database unavailable` error. The verifier, `scripts/staging-generation-6-connection-verifier.mjs`, discards the first connection error, waits 16 seconds, then also replaces the second error with only a role/check label. The Generation 23 wrapper saves that label but omits even the verifier's safe `purposesPassed` count. Query-denial SQLSTATE handling does not cover a connection failure. This is a **confirmed defect in private test diagnostics**. It prevents a defensible claim that the v6 failure was an incorrect password, Supavisor cache, connection limit, network/TLS problem, timeout or client-state mismatch.

**New read-only log evidence:** The existing Supabase CLI access queried `supavisor_logs` via the official Management API for `20:13–20:16 UTC`. A broker `ClientHandler` password-authentication rejection was logged at `20:14:58.797 UTC`, 46 ms before the durable v6 HOLD; a matching `DbHandler` SQLSTATE `28P01` followed at `20:14:59.298`. The customer role had the same initial password rejection at `20:13:57.738` and authenticated after a retry at `20:14:15.025–20:14:15.036`; cart was rejected at `20:14:16.146` and authenticated at `20:14:34.650–20:14:34.658`. The bounded 24-row log response showed no circuit-breaker or client-limit event. A second bounded query for v5 (`19:51–19:56 UTC`, 61 rows) found **all five** newly installed roles initially rejected, then each authenticated about 17–18 seconds later. The query did not expose or save raw credentials. These events strongly establish that the v6 broker retry coincided with a real database authentication rejection, rather than a website, checkout or provider failure. They make delayed Supavisor recognition of fresh role passwords the leading explanation; they do **not** prove why this particular broker retry failed or that its submitted password was correct. No direct broker login was recorded before retirement. The role-setup SQL does compare the installed SCRAM verifier with the generated expected verifier, and independent code review found no broker-only password-mapping defect.

Every supervised run changes passwords on five roles and immediately connects through Supabase's shared transaction pooler at port 6543. Supabase documents a short credential cache after password changes: fresh correct credentials can be rejected, usually resolving after a reconnect in around 15 seconds; occasional retries can fail for longer. The current runtime has a three-second driver timeout and four-second acquisition timeout, and the verifier permits only one 16-second wait/retry. Repeated failed authentication may also trigger a pooler circuit breaker for up to two minutes. The v6 logs point to password/cache handling as the priority, not to a general site defect.

Official references: [Supabase password-rotation guidance](https://supabase.com/docs/guides/troubleshooting/supavisor-error-password-authentication-failed-after-password-rotation), [Supabase circuit-breaker guidance](https://supabase.com/docs/guides/troubleshooting/supavisor-error-circuit-breaker-open-after-password-rotation-0fdb72), [Supavisor log guidance](https://supabase.com/docs/guides/database/supavisor), [Supabase connection limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits).

## The larger process failure

V4, V5 and V6 stopped at **different** real integration points: v4 in surface activation (substep not journaled; later source review found blockers), v5 at an encrypted Vercel setting acknowledgement, then v6 at a broker database connection. Each correction passed local tests, but those tests replaced the exact hosted component that failed next. The local composite test substitutes Docker Postgres for the real Supavisor connection wrapper. Its assembled connection fixture supplies its own password and always accepts `connect()`, so it cannot catch a password-forwarding mismatch or the observed rejection. Thousands of local passes therefore do not prove the complete hosted customer journey. The safety controls and one-use records helped contain each failure, but the repeated full-window setup is an expensive way to discover a single interface mismatch. The independent Astra review agrees that the diagnostic loss and test-boundary mismatch are systemic process faults, not evidence of a single permanent Supabase outage.

No engineer can guarantee a 100% pass through third-party services or an owner sign-in code. The gate for another run should instead be concrete: the failure cause can be observed, the full assembled path has passed its rehearsal, the same temporary credentials work both directly and through the pooler, the deployed consumers have proved their own restricted operations, the owner is present, and shutdown has been proved. Do not issue another generation merely to consume a new record.

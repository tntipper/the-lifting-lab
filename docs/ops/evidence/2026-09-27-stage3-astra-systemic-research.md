## Evidence for the v6 authentication problem

A bounded read-only query of Supabase's `supavisor_logs` found a broker `ClientHandler` password rejection at `20:14:58.797 UTC`, 46 ms before the local HOLD, and an upstream `DbHandler` `28P01` at `20:14:59.298 UTC`. In v6 the new customer and cart credentials were rejected on first attempt, then authenticated after a wait. In v5 **all five** newly installed roles had an initial password rejection, then authenticated roughly 17–18 seconds later. These timestamps make an authentication/pooler-convergence issue the leading explanation for v6. They do not prove the broker's submitted text was correct; no direct broker login was captured before retirement. The bounded v6 log query showed no circuit-breaker or client-limit event, which is limited negative evidence.

[Supabase documents](https://supabase.com/docs/guides/troubleshooting/supavisor-error-password-authentication-failed-after-password-rotation) that its shared pooler may briefly check new correct passwords against cached old credentials; an actual reconnect generally triggers refresh, and some retries may still fail. [Supavisor's public source](https://github.com/supabase/supavisor/blob/main/lib/supavisor/db_handler.ex) treats upstream `28P01` as a reason to invalidate stored secrets and can return `28P01` while waiting for replacement secrets. That public code explains a possible mechanism but has **not** been version-matched to the hosted service. Therefore `28P01` alone is not proof that our application generated a bad password.

The five deliberate wrong-password probes in v5 occurred after its positive connections. Public [Supavisor circuit-breaker guidance](https://supabase.com/docs/guides/troubleshooting/supavisor-error-circuit-breaker-open-after-password-rotation-0fdb72) says repeated failed authentication can temporarily block an origin. Public source currently counts failures by tenant and peer address; its defaults are not proven to match hosted staging. V6 failed **before** these negative probes, so they did not cause the v6 stop. They are a forward-looking risk to readiness and need a subsequent known-good connection proof.

## Why prior reviews missed failures

1. The actual runtime collapses a driver rejection, four-second acquisition timeout and bad post-connect state to one generic error in [`lib/server/staging-postgres.ts`](../../../lib/server/staging-postgres.ts). That is suitable for customer-facing errors but loses needed private diagnosis. The verifier discards the first connection error and reduces the second to role/check in [`scripts/staging-generation-6-connection-verifier.mjs`](../../../scripts/staging-generation-6-connection-verifier.mjs); the Gen23 wrapper keeps only those labels in [`scripts/staging-generation-23-restricted-connections.mjs`](../../../scripts/staging-generation-23-restricted-connections.mjs).
2. The assembled fixture in [`tests/staging-generation-23-assembled-connections.test.mjs`](../../../tests/staging-generation-23-assembled-connections.test.mjs) ignores the incoming password/certificate and makes its fake connection succeed. The composite acceptance test replaces the real connection wrapper with a Docker database proof. Passing them does not prove the Supabase connection path. Earlier independent reviews approved narrow arming changes, not a real end-to-end success probability.
3. The settings metadata checker returns `valuesReadable:false` in [`scripts/staging-generation-23-settings-readback.mjs`](../../../scripts/staging-generation-23-settings-readback.mjs). It proves names, IDs and scope, **not** that the actual website and Edge broker use the generated password. [Vercel states](https://vercel.com/docs/environment-variables/managing-environment-variables) changed environment variables apply only to **new** deployments. The current surface code does create a new enabled Preview after setting changes, so this is not an established missing-redeploy bug; its exact deployed consumer still needs proof. [Supabase states](https://supabase.com/docs/guides/functions/secrets) Edge secrets become available immediately without redeployment.
4. The proposed direct-authentication check cannot run from this Mac as-is. A read-only DNS query found only an AAAA record for the direct staging database; a two-second TCP attempt to that published IPv6 address failed with `errno 65` (no route). [Supabase documents](https://supabase.com/docs/guides/database/connecting-to-postgres) that direct access is IPv6 by default and its shared pooler is IPv4. This is an environment constraint, not a reason to buy the IPv4 add-on by default. The existing setup SQL compares each installed SCRAM verifier with the generated expected verifier, which is useful but not identical to a direct login proof.

## Small compatible implementation sequence

1. **Keep the safeguards that worked.** Retain fixed least-privilege roles, one-hour password expiry, customer controls OFF until readiness, one-use records, explicit shutdown and passwordless retirement. Do not create standing credentials or new role names merely to simplify a test.
2. **Repair the private error chain.** Retain an allow-listed connection operation, attempt number, safe SQLSTATE/network category, elapsed-time bucket and completed-role count from actual runtime through verifier and journal. Keep customer-facing errors generic. Never persist raw messages, credentials, SQL or connection strings. Test both first and second failure, delayed success, timeout, cancellation, late connection after closure and diagnostic-write failure.
3. **Repair the assembled test.** Keep real password generation, projection, runtime, verifier, journal and cleanup. Replace only the external database driver; assert it receives the exact generated password and pinned TLS certificate. Assert secret-shaped fixtures never reach output. Run the complete route with simulated external network replies rather than substituted business logic.
4. **Resolve password-readiness evidence before a hosted window.** If an already approved IPv6-capable environment exists, use a separately reviewed TLS-verified direct checker. Otherwise document a reviewed substitute: exact installed SCRAM-verifier match, actual local password-forwarding proof, classified and bounded Supavisor retries, and a final known-good connection after any deliberate negatives. State clearly that this substitute cannot establish direct authentication. Do not buy networking capacity or weaken TLS just to clear the gate.
5. **Prove deployed consumers.** After setting the temporary values once, verify the new protected Preview built with that window's values and the actual Supabase Edge broker can each perform fixed, read-only identity/privilege checks under customer controls OFF. Return only safe pass/fail fields. No arbitrary SQL, secret echo, customer data or public route activation. Branch-scoped setting names alone are insufficient.
6. **One final supervised journey.** Only after the actual assembled route and hosted readiness pass, use the same unrotated temporary material for owner sign-in, identity/orders, explicit guest-cart transfer, exact product and price, GET-only checkout page and POST logout. Confirm final site/provider/database OFF and all roles passwordless/zero-session. Stop and contain on wrong identity, cross-customer data, unexpected checkout destination, uncertain logout/payment/activation or uncertain shutdown; cosmetic findings can be collected through the end.

**Cost gate:** no new one-use customer window while private failure causes are still indistinguishable, the actual assembled route is unproved, the direct-check alternative is undecided, or deployed consumers have not been covered by a concrete test. Passing unit tests or another narrow arming review alone cannot clear this gate. No one can guarantee external services or owner sign-in will pass 100%; this gate removes the avoidable, known sources of wasted runs.

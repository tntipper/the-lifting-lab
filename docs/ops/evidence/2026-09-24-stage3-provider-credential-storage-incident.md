# Stage 3 provider normalization credential-access incident

The approved provider-normalization launcher was **not invoked**. Neither one-use mutation journal was created. The local arming worktree was disarmed at `c08633e300ab22b8cc711c42d331bc0f7c1b1391`; its nine gates are false and its arming paths match disabled base `be38e13d34a1883aafe30619a631e066a1801086`. The staging provider remained enabled on the last dashboard observation. No provider update, account/cart activation, deployment, purchase or customer message occurred. Hosted state must be refreshed before any later window.

## Cause and contributing decisions

The previous one-hour Vercel API token had expired. During the newly approved credential window, `security add-generic-password -U ... -w` was first used with an assumed stdin password. That option does not consume the piped secret as intended; the fixed Keychain item's password became empty and the command timed out. A later command supplying the password as an argument also timed out. The process decision was to try a Keychain update method without first proving its input semantics on a disposable, non-secret item.

The GUI recovery initially mistook Keychain Access's editable **Comments** field for its protected password field. The new token was pasted into Comments and saved briefly. The Comments field was cleared and a metadata-only check returned `COMMENT_CLEARED`; the token was then placed in the actual password field and the clipboard was cleared. One CUA accessibility result displayed the Comments value in the local tool transcript. Treat this as transient local secret exposure, not as proof that the token stayed private. The token was scoped to the `the-lifting-lab` Vercel project and set to expire after one hour; the owner's instruction to let that one-hour token expire naturally is retained. No token value belongs in this record.

After the owner allowed `/usr/bin/security` for this Keychain item, a direct metadata-free read returned `KEYCHAIN_TOKEN_READ_PASS`. A subsequent three-credential check held on the Vercel item, and the launcher's **exact Python Keychain reader**, called without the launcher or journals, returned `EXACT_READER_HOLD`. The helper intentionally hides its underlying exception, so its result alone does not prove whether the failure was a Keychain timeout, denial or another subprocess error. The immediate launch blocker is unreliable per-process Keychain access. Whether macOS prompt/ACL state, process environment or a second Keychain condition caused it remains unproved. A single successful direct read did not establish reliable access for the actual launcher.

## Recovery and prevention gate

The operator stopped before invoking the armed launcher, then disarmed it. The fixed item retained “Confirm before allowing access” with only `/usr/bin/security` listed on the last UI observation; the Keychain Comments field and clipboard were cleared. No mutation journal exists. The disarmed launcher returned `PROVIDER_NORMALIZATION_LIVE_DISABLED`; activation manifest, live-boundary and `git diff --check` passed, and the disarmed source/manifest match the disabled base. Preserve the local arming and disarming commits as evidence; do not push either.

This incident remains **OPEN/HOLD**. Before any successor provider-mutation credential window, determine the actual cause of the intermittent access or replace the access path with a reviewed, deterministic method. A separately approved, local-only readiness diagnostic is part of this still-open investigation, not a successor mutation attempt. Its own bounded mode-0600 receipt may be consumed once to gather all-selector access evidence; it must not create or consume either provider-mutation journal. The diagnostic must exercise **all three selectors** through the launcher's exact Python executable, arguments, environment and timeouts without printing secrets. A PASS would prove access in that one window only, not explain or prevent the historical intermittent failure. Independently review the root-cause finding and preventive control before any fresh provider-mutation identifier or journal is considered. Do not use `security ... -w` with stdin to set a password, enter a secret in Keychain Comments, or infer readiness from a direct shell read. If the access method changes, revise the disabled source and stage plan, run focused checks, obtain independent review of the resulting diff, and get fresh action-time approval. Never consume a provider-mutation journal just to diagnose credential access. The failed exact-helper check and clean disarm prove the current stop control worked; they do **not** prove a replacement method yet.

Remaining uncertainty: the token's transient appearance in a local CUA output, the precise reason for the earlier helper failure, and fresh hosted state after this window. These must be considered before any successor stage. The token expires naturally; no claim is made that the local transcript can be erased.

## Local diagnostic outcome, 24 September

The separately approved all-selector credential-readiness V1 diagnostic ran once and returned a terminal PASS through the exact bundled Python helper parameters. Its separate mode-0600 receipt is preserved; both provider-mutation receipts remain absent, and the local arming checkout was disarmed and verified. See `docs/ops/evidence/2026-09-24-stage3-credential-readiness-v1-result.md`. This narrows the issue to an intermittent or previously changed condition; it does **not** establish which condition caused the earlier failure, prove token validity, or close this incident. Do not repeat the consumed diagnostic or proceed to provider mutation on PASS alone. Independently review the discrepancy and establish a preventive access method before a successor mutation window.

Independent discrepancy review confirmed that the earlier stdin-based Keychain provisioning produced an empty password and that later GUI recovery put token text in Comments. Those storage errors were corrected before the V1 PASS. The later exact-helper failure remains unclassified: the command, selectors, restricted environment and ten-second `/usr/bin/security` timeout were unchanged between failed and successful attempts. Fixed exit categories and output wiping improved diagnosis but did not repair a proved access defect. The reviewer therefore kept the incident-learning gate **HOLD**. A proposed replacement is a bounded native Keychain reader that forbids authentication UI and returns classified failure before any provider intent; its compatibility with the Mac's existing file-based login keychain and any exact application ACL must be qualified and reviewed before use. The disabled source and build have since been implemented; see the dated result below.

## Disabled diagnostic follow-up

Later secret-suppressed direct reads succeeded under both normal and restricted `PATH`/`LANG` environments (initially 4.3 and 4.4 seconds; subsequent reads were immediate). The restricted environment is therefore compatible with retrieval at those moments, but neither the earlier exact-helper cause nor cold-start reliability is established. Keychain metadata and generic system logs did not resolve the cause. The helper now returns fixed exit categories for guard, timeout, command, format, output and unexpected failures, without printing a credential or raw error. An isolated test replaces the native command with `/bin/false` before import and proved all six process exits, unchanged success bytes, empty failure output and buffer handling; 7/7 tests passed. Activation manifest, live-boundary, focused session tests and typecheck passed while disabled. Independent review returned GO for this **diagnostic repair only**. The incident stays OPEN/HOLD until a separately reviewed all-selector readiness process and the protocol's incident-learning gate are satisfied. No provider-mutation journal was created.

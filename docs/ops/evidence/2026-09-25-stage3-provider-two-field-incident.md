# Staging provider two-field attempt: disabled, JWKS retained

Date: 2026-09-25. Scope: staging project `qdmvngjwkcsilzmqksme`, custom provider `custom:tll-staging-subject-broker-v1`. Production was untouched.

After an independent review and a **new** owner approval, the one-run Supabase-only launcher returned `RECONCILIATION_REQUIRED`. The private intent journal `../implementation-state/staging/tll-provider-supabase-only-v1.json` is consumed in state `RECONCILIATION_REQUIRED`; its separate phase journal is consumed at `UPDATE_DISPATCH` with outcome `RECONCILIATION_REQUIRED`. **Never replay either journal or resend the same update.** The launcher and shared Keychain reader were immediately restored to `false`, the isolated tracked tree was clean, the generated manifest matched, and the live-boundary check passed.

A fresh Supabase dashboard reload then showed the provider **DISABLED**. Opening its settings without saving showed the previous staging JWKS URI still populated. That is direct UI evidence of a partial change, not a full official API readback. The update had requested only `enabled:false` and `jwks_uri:''`; the strict native adapter rejected the update response before acknowledgement because the required two-field result was not present. No customer/cart switches were enabled.

**Root cause supported by primary source:** the published Supabase Auth server [custom-provider update handler](https://github.com/supabase/auth/blob/ce9a8eee0cc042be8c7a42981a7ddae631e41d91/internal/api/custom_oauth_admin.go#L629-L634) applies a JWKS change only when its value is non-empty. The same handler accepts `enabled:false` through a non-nil boolean. This exactly predicts the observed disabled provider with the old JWKS retained. The installed JavaScript SDK forwards the supplied update body; the hosted server version has not been independently identified, so this is a strong source-supported explanation rather than proof of its deployed binary. Published [runtime code](https://github.com/supabase/auth/blob/ce9a8eee0cc042be8c7a42981a7ddae631e41d91/internal/api/external.go#L732-L735) rejects a disabled custom provider during sign-in.

**What remains unproved:** the complete current provider object from an official read-only GET, whether any field besides enabled changed, and whether the hosted service uses the exact published handler. The intent journal stores a hash of the preread, not the whole earlier provider object, so exact historical full-field comparison cannot be reconstructed after the fact. Do not claim the original two-field acceptance condition passed.

**Next gate:** design and independently review a separate, read-only official provider observation with a new one-use journal and fresh owner approval. Compare its current fields with the pinned staging contract and the UI observation. Then revise the acceptance rule to an explicit safe-held state if warranted: disabled provider, known retained JWKS, no account/cart activation, and a documented path for eventual replacement. Do not delete/recreate the provider, write directly to the Auth database, or repeat an empty-string JWKS update without a separate evidence-backed plan.
